# Service Leaf SEO and Page Quality

SEO here means making the page easy for a person and a search engine to identify, trust, and distinguish. It does not mean maximizing keyword occurrences.

## Intent architecture

Assign one primary problem to one canonical leaf URL. Supporting intents may share the page when they need substantially the same evidence, procedure, and attorney work. Split nothing into a new URL without user-approved IA.

Reject or merge a plan when it would create:

- a near-duplicate page differing only by keyword or city;
- a page that funnels immediately to another page without unique help;
- paragraphs whose only purpose is exact-match repetition;
- a regional claim unsupported by office location or actual service facts.

`창원` may be used where local service context is real. Do not append 마산·진해·김해·양산·거제·통영·부산 lists merely to rank for places.

## Search-result fields

- **Title**: unique, concise, accurate, and aligned with the H1. Lead with the visitor's recognizable subject; add office/brand or a relevant verified credential only when useful.
- **H1**: one clear visible page title. Do not make it a keyword inventory.
- **Description**: one or two natural sentences summarizing the page's distinctive scope and help. Make every leaf description unique. Search engines may choose visible page text instead.
- **Canonical**: use the existing site convention and the final public URL. Do not add ad hoc canonicals that contradict routing.
- **Open Graph**: keep title and description consistent with the page when the project supports them.
- **Meta keywords**: do not add them as an SEO deliverable.

Do not optimize to a mythical fixed character count. Check mobile readability and truncation risk, but prefer a complete, page-specific summary.

## Visible content

- Put a direct answer and the page's scope near the top.
- Use headings that describe decisions or topics, not decorative slogans.
- Keep important answer text visible by default when practical; do not hide the entire useful page behind interactions.
- Use terminology a client searches for, then explain it in plain Korean.
- Make every FAQ answer independently useful and consistent with the main text.

## Internal links

Add a link only when it helps the next decision. Prefer:

- `/about/lawyer` when a relevant profile claim is used;
- a closely related service leaf when the boundary between matters is genuinely useful;
- a published, factually relevant case page when consent and compliance requirements are met;
- the services hub for broader orientation.

Write descriptive Korean anchor text. Avoid repeated `자세히 보기` when the destination can be named.

## Structured data

Use only types supported by the site's established architecture and make markup match visible content exactly. Breadcrumb markup is useful when it reflects the real hierarchy. FAQ markup does not guarantee a rich result and must not motivate redundant FAQ text. Validate JSON-LD syntax after changes.

## Official guidance to re-check

Because search behavior changes, verify current versions when implementing or making a claim:

- Google Search Central: [SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide), [title links](https://developers.google.com/search/docs/appearance/title-link), [snippets](https://developers.google.com/search/docs/appearance/snippet), [spam policies](https://developers.google.com/search/docs/essentials/spam-policies), and [structured-data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies);
- Naver Search Advisor: [content recommendations](https://searchadvisor.naver.com/guide/content-basic), [SEO basics](https://searchadvisor.naver.com/guide/seo-help), and [SEO report guidance](https://searchadvisor.naver.com/guide/report-seo).

Never promise ranking, indexing time, a displayed snippet, or a rich result.
